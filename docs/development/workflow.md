# Standard workflow for any agent or person

ทุกคนที่แก้โปรเจกต์นี้ ไม่ว่าจะเป็น AI ตัวไหนหรือคน ทำงานตามรูปแบบเดียวกันนี้
กติกาบังคับอยู่ใน [AGENTS.md](../../AGENTS.md); ไฟล์นี้บอก "ทำอย่างไร" ให้ได้ผลลัพธ์รูปแบบเดียวกัน
ถ้าเครื่องมือของคุณอ่านไฟล์กติกาชื่ออื่น (เช่น CLAUDE.md) ให้ไฟล์นั้นชี้มาที่ AGENTS.md ไม่คัดลอกกติกาไปซ้ำ

## 1. ลำดับการทำงานหนึ่งงาน

1. **เริ่ม**: `git status --short` ต้องว่างหรือรู้ว่าไฟล์ไหนของใคร; `git log --oneline -3` จด commit ตั้งต้น
2. **อ่าน**: [index](../index.md) → เอกสารเจ้าของเรื่อง 1–2 ไฟล์ → source/เทสที่เอกสารชี้ ไม่อ่านทั้ง repo
3. **baseline**: รันเทสของส่วนที่จะแก้ก่อนแก้ ถ้าล้มอยู่แล้วให้จดไว้ว่าไม่ใช่งานของเรา
4. **แก้ทีละงานย่อย**: แต่ละงานย่อยต้องจบด้วย เทสผ่าน + commit ไม่สะสมงานหลายเรื่องแล้วค่อย commit
5. **เทสพฤติกรรม**: ทุกการแก้มีเทสที่ล้มกับโค้ดเดิมและผ่านกับโค้ดใหม่ รวมเคสซ้ำ/เวลา/crash ที่เกี่ยวข้อง
6. **ตรวจตามขอบเขต**: scope เล็กสุดก่อน ([Test selection](test-selection.md)); เปลี่ยนหลายระบบหรือส่งมอบ ใช้ `--scope all` ครั้งเดียวตอนจบ
   แก้ error เล็ก ๆ ให้รันซ้ำเฉพาะเคสที่ล้ม (`--match`) แล้วจึง scope ของไฟล์ที่แก้ ไม่รันทั้งระบบใหม่
   ไม่เปิด server เอง: เทสและ Playwright เปิด/ปิด server ทดสอบให้เอง; แก้แค่เอกสารไม่ต้องรันเทส runtime
7. **UI เปลี่ยน**: build แล้วปิดเปิด desktop ตาม [Setup](setup.md) และตรวจหน้าต่างใหม่
8. **เอกสาร**: แก้เอกสารเจ้าของเรื่องในที่เดิม แยก ทำแล้ว/วางแผน/ตรวจจริงแล้ว/ยังไม่ตรวจ
9. **รายงาน**: ตามรูปแบบในข้อ 5

## 2. แผนงานที่จะส่งต่อให้ผู้อื่น (AI หรือคน)

แผนอยู่ใน `docs/planning/<เรื่อง>.md` และลิงก์จาก index ใช้หัวข้อตามนี้เสมอ:
- **สถานะตั้งต้น**: commit, อะไรทำแล้ว (ตรวจแล้ว), อะไรยังไม่มี
- **กติกาเฉพาะรอบ**: สิ่งที่ห้ามทำเพิ่มจาก AGENTS.md (เช่น ห้าม push, ห้าม migration)
- **งาน T1..Tn**: แต่ละข้อมี ไฟล์ที่แก้, ขั้นตอนเป็นข้อ, เทสที่ต้องเพิ่ม, คำสั่งตรวจ, ข้อความ commit
- **ลำดับความสำคัญ**: ถ้าเวลาไม่พอ ข้อไหนข้ามได้
- **หยุดและรายงานเมื่อ**: เงื่อนไขที่ห้ามตัดสินใจเอง
ถ้าผู้รับงานเป็น model ที่ไม่เก่งมาก ให้แยกคำสั่งที่พิมพ์ได้ตรงตัว (runbook) และตาราง error→การแก้ (troubleshooting) เป็นไฟล์คู่กัน
ตัวอย่าง: [P4 plan](../planning/p4-integration.md), [runbook](../planning/p4-runbook.md), [troubleshooting](../planning/p4-troubleshooting.md)

## 3. Commit

- หนึ่ง commit = หนึ่งเรื่องที่ review ได้; `git add <ไฟล์>` ทีละไฟล์ ห้าม `git add -A` เมื่อมีงานคนอื่นใน tree
- หัวเรื่อง: `<type>: <สิ่งที่เปลี่ยน>` โดย type เป็น `feat`, `fix`, `test`, `docs`, `chore`
- เนื้อหา: ทำไม (ปัญหาเดิม), เปลี่ยนอะไร, และบรรทัด `Checks:` ที่มีคำสั่ง ผล และเวลาเป็นวินาทีตามจริง
- ห้ามเขียนว่าผ่านถ้าไม่ได้รัน; ถ้าบางอย่างไม่ได้ตรวจ ให้เขียน "Not covered: ..."
- push เฉพาะเมื่อเจ้าของสั่ง และ `git fetch` ตรวจว่า remote ไม่มี commit ใหม่ก่อน

## 4. เมื่อเจอ error

1. อ่าน error ให้จบ จดข้อความและ code; อย่าเดา
2. ตรวจว่าเกี่ยวกับงานเราไหม (`git diff --stat`); ถ้าไม่เกี่ยว รายงาน ไม่แก้ของคนอื่น
3. แก้ที่สาเหตุ ไม่ใช่ที่อาการ: ห้ามลบ assertion, เพิ่ม sleep, ใช้ `any`/`@ts-ignore`/`noqa`, หรือ catch ทิ้งเงียบ
4. รันเฉพาะเทสที่ล้มซ้ำ; ผ่านแล้วจึงรัน scope ที่เกี่ยวข้อง
5. แก้ 2 รอบแล้วยังล้ม → หยุด รายงานพร้อม error, สิ่งที่ลอง และสมมติฐาน
6. Error code ของระบบดูความหมายจาก `GET /api/errors` หรือ [errors.py](../../backend/smartflow/errors.py) และ [Errors](../operations/errors.md)

## 5. รูปแบบรายงานท้ายงาน

```
สรุป: <หนึ่งประโยคว่าทำอะไรได้ผลอย่างไร>
Commits: <hash> <หัวเรื่อง> (ทีละบรรทัด)
ตรวจแล้ว: <คำสั่ง> → <ผล> (<วินาที> s)  (ทีละบรรทัด)
หลักฐานแยกชั้น: unit/E2E | desktop activation | real Chrome | packaged EXE | clean Windows | provider จริง
ยังไม่ทำ/ไม่ได้ตรวจ: <รายการ>
ต้องให้เจ้าของตัดสินใจ: <รายการ>
```

## 6. งานพร้อมกันหลายคน

ใช้ [Parallel sessions](parallel-work.md): แยก worktree/branch หรือประกาศไฟล์ที่เป็นเจ้าของ
ห้ามแก้ไฟล์ที่คนอื่นกำลังแก้ ห้าม regenerate ไฟล์ส่วนกลางจาก tree ที่มีงานคนอื่นปน
